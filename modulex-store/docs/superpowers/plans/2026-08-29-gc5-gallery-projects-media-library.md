# GC-5 Gallery / Projects + Media Library Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete GC-5 by connecting the existing Gallery/Projects CMS to reviewed GC-2 Media Library assets, hardening project publication/public projections, curating at least one real parent-attributed residential portfolio in production, and closing Gallery/Projects production acceptance without starting GC-6.

**Architecture:** Keep `store_projects` and `store_project_media` as the canonical project domain. Add Media Library asset identities and project attribution, enforce published-project validity in PostgreSQL, expose projects through public `SECURITY INVOKER` wrappers backed by private implementations, migrate Admin image selection from arbitrary uploads/URLs to eligible published Media Library assets, and preserve the existing fail-closed Store Gallery readiness contract. Extend the controlled GC-2 intake allow-list for approved GC-1 residential candidates; human review and explicit asset/project publication remain mandatory.

**Tech Stack:** Next.js 16, React 19, TypeScript, Supabase/PostgreSQL/RLS/Storage, `@supabase/supabase-js`, Node contract scripts, Sharp `0.35.4`, Vercel.

**Spec:** `modulex-store/docs/superpowers/specs/2026-08-29-gc5-gallery-projects-media-library-design.md`

## Global Constraints

- Start from and continuously reconcile against current `main`; design baseline was `cc6be581ca68c0e59f6a076e23d0cd8341c5fe05` after PR #144.
- Preserve PR #143 multi-role RBAC. Never authorize Store project management by comparing only `profile.role`; use effective `profile.roles` + `hasPermission(..., "store.manage")` in Admin UI and `private.current_user_has_any_role(...)` in database policies.
- Keep `store_projects` / `store_project_media`; do not create a parallel Granite-specific project CMS.
- Project image publication source of truth is `store_media_assets.id`, not arbitrary browser-provided image URLs.
- Project images are eligible only when Media Library state is `published`, `media_type = 'image'`, `cabinet_relevance = 'relevant'`, public locator is valid, and attribution is `oakwell_owned` or `parent_attributed`.
- `mixed` assets may remain valid GC-2 assets but are not GC-5 project-publishable.
- Parent-attributed projects must visibly identify the source and provide an `https://` source page before publication.
- Do not invent project client names, job addresses, dates, cabinet brands, installation/completion claims, service area, pricing, lead time, guarantee, or Oakwell authorship.
- Countertop-only candidates remain excluded; Commercial Projects remain hold.
- Keep direct anonymous access to project/media/Media Library tables denied.
- Keep public functions narrow with explicit grants/revokes; privileged implementations belong in a non-exposed schema.
- Preserve the existing Gallery fail-closed behavior until both a published `gallery` page and at least one valid published project exist.
- Controlled intake remains an allow-list; never accept an arbitrary remote source URL from the browser.
- Intake never auto-approves, auto-publishes, or auto-associates a project.
- Customer file upload, Dealer supporting-document reuse, appointments, and GC-6 customer-journey content are out of scope.
- Generate the GC-5 migration with `supabase migration new gc5_gallery_projects_media_library`; use the exact generated filename from the command for all subsequent steps. Do not hand-invent a timestamped migration filename.
- Run Supabase Security/Performance Advisor after production migration and resolve every new GC-5-specific finding before closeout.
- Do not merge/deploy the implementation PR automatically unless explicitly authorized by the user.
